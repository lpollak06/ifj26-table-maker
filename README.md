# IFJ26 Table Maker

Interactive helper for designing the LL(1) table and the precedence table of the IFJ26 compiler.
Not part of the compiler itself.

Live on the tailnet only: `https://<tailnet-host>:4310/` (the deploy script prints the exact URL).

## Stack

- TanStack Start + TanStack Router (React 19, SSR, server functions), Vite, Tailwind CSS v4
- SQLite through Node's built-in `node:sqlite` (Node ≥ 22.13), no native addons
- UI components from [React Bits](https://www.reactbits.dev/) (TS + Tailwind variants), vendored unmodified in
  `src/components/reactbits/`: GooeyNav, SpotlightCard, StarBorder, ShinyText, ClickSpark, CountUp, SwipeToast, Aurora

## Layout

| Path | Purpose |
| --- | --- |
| `src/lib/analysis.ts` | Grammar module: definition texts (N, T, S) + rules P in, one analysed G = (N, T, P, S) out (`analyzeGrammar`) |
| `src/lib/symbols.ts` | Symbol syntax: lexing, quoting, `#` comments, ε-words and arrows |
| `src/lib/grammar.ts` | Rule parser, Empty/First/Follow/Predict, LL table, LL checks and LL simulation |
| `src/lib/definition.ts` | N/T declaration syntax (parse, append, format, C enum paste) |
| `src/lib/grammarOps.ts` | Definition-tab operations as pure functions (textbook example, fill N/T from rules) |
| `src/lib/precedence.ts` | Precedence table module (terminals, relations, `$`), checks, precedence simulation |
| `src/lib/precOps.ts` | Precedence-tab operations as pure functions (G_expr2 example) |
| `src/lib/tableModel.ts` | Shared table model (LL table, sets, Predict, precedence) with conflict flags and tooltips |
| `src/lib/exports.ts` | Markdown / CSV / LaTeX / C / PNG exports through one `buildExport` entry |
| `src/lib/png.ts` | Table model → PNG (canvas, scale capped for iOS Safari) |
| `src/lib/project.ts` | Project document codec: defaults, versioned decode (v1 → v2), file import, per-project view state |
| `src/lib/projectSession.ts` | Client project session: framework-free state machine for the live document, debounced saves, retries, conflicts |
| `src/lib/projectTransport.ts` | Transport port of the session; `.rpc.ts` = server-function adapter, `.fake.ts` = in-memory fake for tests |
| `src/lib/useProjectSession.ts` | React binding of the session (`useSyncExternalStore`, page-hide flush, unsaved-changes guard) |
| `src/server/db.server.ts` | `openDatabase()`: SQLite connection (WAL) + migrations (`PRAGMA user_version`) |
| `src/server/projects.server.ts` | Project store: projects, revision check, snapshots (auto / named / safety), view state |
| `src/server/projects.functions.ts` | Server functions (RPC) called by the UI, input validation |
| `src/start.ts` | Start instance with a CSRF (Fetch Metadata) check on server functions |
| `vite.config.ts` | Vite + Nitro config, security headers (CSP, `X-Frame-Options`, …) on every response |
| `src/components/` | Tab components and UI helpers; `reactbits/` holds the vendored React Bits components |
| `src/routes/` | `/` project list, `/p/$projectId?tab=def\|overview\|ll\|prec\|export\|history` editor (`&mode=sim\|view` for LL) |
| `deploy/` | systemd unit and deploy script |

Each project is one JSON document in the `projects` table. Saves are debounced and use a revision
number, so two tabs or two people editing the same project get a conflict prompt instead of silently
overwriting each other. An automatic backup is kept at most every 20 minutes (last 30), and named
versions can be saved and restored on the History tab. These snapshots live in the same database file, so
they are not backups – see [Deployment](#deployment) for those. Project JSON files from the original
single-file `tools/table-maker.html` can be imported.

## Development

```sh
npm install
npm run dev        # http://localhost:3000, database in ./data/table-maker.db
npm run typecheck
npm test           # vitest (npm run test:watch while developing)
npm run build      # Node server in .output/
```

`TABLE_MAKER_DB` overrides the database path, `HOST` / `PORT` the listen address.

## Deployment

```sh
deploy/deploy.sh                          # build HEAD and switch to it (default ssh host: t3-exec)
deploy/deploy.sh --allow-dirty            # same, although the working tree has uncommitted changes
deploy/deploy.sh --rollback               # switch back to the previous release
deploy/deploy.sh --rollback --restore-db  # … and also put back the database from before the current release
deploy/deploy.sh --help
```

The script deploys a **commit**, not the working tree: it refuses a dirty tree (with `--allow-dirty` it still
ships only `HEAD`, uncommitted changes are left out) and refuses commits that track `node_modules/`, `data/`,
`.env*`, `*.local` or SQLite files. `git archive HEAD` is unpacked into `~/.cache/table-maker-build/<sha>` on the
VM (a dedicated build dir, never the checkout in `~/build/table-maker`), where `npm ci`, typecheck, tests and
build run. So commit before deploying, including changes to the unit or the script itself.

On the VM:

| Path | Content |
| --- | --- |
| `/opt/table-maker/releases/<sha12>/` | Built server output, `REVISION` (deployed commit), the unit it was built with, `PRE_DEPLOY_BACKUP` |
| `/opt/table-maker/current`, `previous` | Symlinks to the running and the previous release (last 5 releases kept) |
| `/var/lib/table-maker/table-maker.db` | The database (really `/var/lib/private/table-maker/`, owned by the dynamic user) |
| `/var/backups/table-maker/<UTC time>-<label>/` | Database backups, root-only, last 10 kept (plus the ones `current`/`previous` refer to) |

Every deploy and rollback stops the service, copies the database (with its `-wal`/`-shm`), folds the WAL into
the copy, runs `PRAGMA integrity_check` on it and records its schema version – before any new code (and so any
migration) runs. Then `current` is switched, the unit installed, the service started, `127.0.0.1:4310` checked
and `tailscale serve` (re)published. A failure after the stop starts the service again. Redeploying a commit
that is already built reuses its release.

Rollback swaps `current` and `previous` (running it again rolls forward). If the current release migrated the
database (its schema version is newer than in the backup taken right before it was activated), a plain
`--rollback` refuses; `--rollback --restore-db` restores that backup – edits made since that deploy are lost,
but the state right before the rollback is backed up first. To restore some other backup by hand:

```sh
sudo systemctl stop table-maker
sudo rm -f /var/lib/table-maker/table-maker.db-wal /var/lib/table-maker/table-maker.db-shm
sudo install -m 600 -o "$(sudo stat -c %u /var/lib/private/table-maker)" -g "$(sudo stat -c %g /var/lib/private/table-maker)" \
  /var/backups/table-maker/<backup>/table-maker.db /var/lib/table-maker/table-maker.db
sudo systemctl start table-maker
```

The service runs `/usr/local/bin/node` (checked to be ≥ 22.13 with `node:sqlite` before every start), listens
on `127.0.0.1:4310` only and runs as a sandboxed dynamic user (no capabilities, `@system-service` syscall filter,
read-only system). `tailscale serve` publishes it over HTTPS to the tailnet on port 4310. It's not reachable
from the LAN or the internet.

Useful commands on the VM:

```sh
systemctl status table-maker
journalctl -u table-maker -f
cat /opt/table-maker/current/REVISION
ls /var/backups/table-maker
tailscale serve status
systemd-analyze security table-maker
```
