# IFJ26 Table Maker

Interactive helper for designing the LL(1) table and the precedence table of the IFJ26 compiler.
Not part of the compiler itself.

Live on the tailnet only: `https://<tailnet-host>:4310/` (the deploy script prints the exact URL).

## Stack

- TanStack Start + TanStack Router (React 19, SSR, server functions), Vite, Tailwind CSS v4
- SQLite through Node's built-in `node:sqlite` (Node ≥ 22.13), no native addons
- UI components from [React Bits](https://www.reactbits.dev/) (TS + Tailwind variants), vendored unmodified in
  `src/components/reactbits/`: GooeyNav, SpotlightCard, StarBorder, ShinyText, ClickSpark, CountUp, SwipeToast, Aurora

Each project is one JSON document in the `projects` table. Saves are debounced and use a revision
number, so two tabs or two people editing the same project get a conflict prompt instead of silently
overwriting each other. An automatic backup is kept at most every 20 minutes (last 30), and named
versions can be saved and restored on the History tab. These snapshots live in the same database file, so
they are not backups – see [Deployment](#deployment) for those. Project JSON files from the original
single-file `tools/table-maker.html` can be imported.

### Drafts

A **draft** is a labelled, editable copy of a project's four parts (definition, grammar rules, precedence table,
reduction rules) made by an agent or by the human; export naming and simulation inputs stay with the project. A
project can have several open drafts (the project list shows how many; the editor's switcher opens them as
`/p/$projectId?draft=<id>`). Both the agent and the human edit an open draft; edits are saved per part with a
revision, so an edit based on an old revision of a part is refused instead of overwriting it. A draft view polls
for agent edits every few seconds, and every draft tab has a **Zmeny oproti projektu** toggle that shows what
adopting the draft would do to the project as it is now.

- **Adopt** (human only): the adopt dialog ticks the parts the draft changed. Parts the draft did not change are
  shown as unchanged and can't be ticked – also when the project changed them since the draft was made, so adopting
  never reverts newer project work. Parts changed on both sides start unticked with a warning. Adopting takes a
  safety snapshot of the project first (`Pred prevzatím návrhu …`), writes only the ticked parts and ends the draft.
  If the project changed meanwhile, the adoption is refused and the dialog recomputes against the fresh project.
- **Discard** ends a draft without touching the project.
- **Draft history**: each draft has its own snapshots (auto, named, safety before a restore) on its own History tab;
  restoring changes only the draft. When a draft ends its last state is kept as a final snapshot.
- **Ended drafts** (adopted or discarded) are read-only. Their histories stay on the History tab, where a version can
  be restored into a new draft (forked from the project's current state) or the whole history deleted.

## Agent interface (MCP)

AI agents (Claude Code, Claude Desktop, …) can read every project through an MCP endpoint served by the running
app at `/mcp`: `https://<tailnet-host>:4310/mcp` when deployed, `http://localhost:3000/mcp` in development. It
speaks MCP over Streamable HTTP in stateless mode (POST only, JSON responses) and goes through the same project store
as the UI. There is no token: whoever can reach the app on the tailnet can use it (ADR 0001). Requests a browser marks
`Sec-Fetch-Site: cross-site` or `same-site` are refused, as for the server functions, so a web page can't drive it.

**Claude Code**

```sh
claude mcp add --transport http table-maker https://<tailnet-host>:4310/mcp
```

**Claude Desktop**: custom connectors added in Settings are called from Anthropic's servers, which can't reach the
tailnet, so bridge it locally with `mcp-remote` in `claude_desktop_config.json`:

```json
{ "mcpServers": { "table-maker": { "command": "npx", "args": ["-y", "mcp-remote", "https://<tailnet-host>:4310/mcp"] } } }
```

Tools take a **target**: `{"kind": "project", "id": "…"}`, `{"kind": "draft", "id": "…"}` or
`{"kind": "snapshot", "id": 12}` (a snapshot of a project or of a draft). Drafts and snapshots are read with their
project's current export naming and simulation inputs.

- Find: `list_projects` (with each project's number of open drafts), `list_snapshots` (of a project or a draft),
  `get_part` (definition, grammar rules, precedence table, reduction rules), `get_project_settings` (export naming and
  simulation inputs, read-only)
- Analyse: `get_ll_table`, `get_sets`, `get_prec_table`, `get_problems`, `export` (Markdown, CSV, LaTeX, C; no PNG)
- Simulate: `simulate_ll`, `simulate_prec`: the input is an argument, and the full trace is returned. They never change
  the project or its saved simulation inputs.
- Changes: `get_draft_changes` – what adopting a draft would do to the project as it is now, in the shape the human
  sees (per-part flags, line diffs, precedence cells, LL table and set changes).
- Drafts: `list_drafts`, `create_draft`, `relabel_draft`, `discard_draft`, and the edits `set_definition`,
  `set_grammar_rules`, `set_reduction_rules`, `set_prec_terminals`, `set_relation`, `clear_relations`. Every edit
  returns the draft's new revision and its fresh problems. Whole-text edits take an optional `expectedRevision`: if
  that part changed after the given revision (say, the human edited it), the edit is refused with the current text,
  to merge and retry; changes to other parts don't matter.

**Drafts only.** An agent never changes a project: it proposes changes in a draft, and only the human adopts.
Adopted or discarded drafts and snapshots are read-only. There is no tool to create, rename, delete or duplicate
projects, adopt drafts, restore or delete snapshots, or change export naming or simulation inputs; calling such a
tool returns an error that says so.

Quick check with curl:

```sh
curl -s -X POST http://localhost:3000/mcp -H 'content-type: application/json' \
  -H 'accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"list_projects","arguments":{}}}'
```

## Development

```sh
npm install
npm run dev        # http://localhost:3000, database in ./data/table-maker.db
npm run typecheck
npm test           # vitest (npm run test:watch while developing)
npm run build      # Node server in .output/
```

`TABLE_MAKER_DB` overrides the database path, `HOST` / `PORT` the listen address.

## Deployment

```sh
deploy/deploy.sh                          # build HEAD and switch to it (default ssh host: t3-exec)
deploy/deploy.sh --allow-dirty            # same, although the working tree has uncommitted changes
deploy/deploy.sh --rollback               # switch back to the previous release
deploy/deploy.sh --rollback --restore-db  # … and also put back the database from before the current release
deploy/deploy.sh --help
```

The script deploys a **commit**, not the working tree: it refuses a dirty tree (with `--allow-dirty` it still
ships only `HEAD`, uncommitted changes are left out) and refuses commits that track `node_modules/`, `data/`,
`.env*`, `*.local` or SQLite files. `git archive HEAD` is unpacked into `~/.cache/table-maker-build/<sha>` on the
VM (a dedicated build dir, never the checkout in `~/build/table-maker`), where `npm ci`, typecheck, tests and
build run. So commit before deploying, including changes to the unit or the script itself.

On the VM:

| Path | Content |
| --- | --- |
| `/opt/table-maker/releases/<sha12>/` | Built server output, `REVISION` (deployed commit), the unit it was built with, `PRE_DEPLOY_BACKUP` |
| `/opt/table-maker/current`, `previous` | Symlinks to the running and the previous release (last 5 releases kept) |
| `/var/lib/table-maker/table-maker.db` | The database (really `/var/lib/private/table-maker/`, owned by the dynamic user) |
| `/var/backups/table-maker/<UTC time>-<label>/` | Database backups, root-only, last 10 kept (plus the ones `current`/`previous` refer to) |

Every deploy and rollback stops the service, copies the database (with its `-wal`/`-shm`), folds the WAL into
the copy, runs `PRAGMA integrity_check` on it and records its schema version – before any new code (and so any
migration) runs. Then `current` is switched, the unit installed, the service started, `127.0.0.1:4310` checked
and `tailscale serve` (re)published. A failure after the stop starts the service again. Redeploying a commit
that is already built reuses its release.

Rollback swaps `current` and `previous` (running it again rolls forward). If the current release migrated the
database (its schema version is newer than in the backup taken right before it was activated), a plain
`--rollback` refuses; `--rollback --restore-db` restores that backup – edits made since that deploy are lost,
but the state right before the rollback is backed up first. To restore some other backup by hand:

```sh
sudo systemctl stop table-maker
sudo rm -f /var/lib/table-maker/table-maker.db-wal /var/lib/table-maker/table-maker.db-shm
sudo install -m 600 -o "$(sudo stat -c %u /var/lib/private/table-maker)" -g "$(sudo stat -c %g /var/lib/private/table-maker)" \
  /var/backups/table-maker/<backup>/table-maker.db /var/lib/table-maker/table-maker.db
sudo systemctl start table-maker
```

The service runs `/usr/local/bin/node` (checked to be ≥ 22.13 with `node:sqlite` before every start), listens
on `127.0.0.1:4310` only and runs as a sandboxed dynamic user (no capabilities, `@system-service` syscall filter,
read-only system). `tailscale serve` publishes it over HTTPS to the tailnet on port 4310. It's not reachable
from the LAN or the internet.

Useful commands on the VM:

```sh
systemctl status table-maker
journalctl -u table-maker -f
cat /opt/table-maker/current/REVISION
ls /var/backups/table-maker
tailscale serve status
systemd-analyze security table-maker
```
